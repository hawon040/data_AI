# TourLink 종합 보고서

> 「빅데이터와 AI」 2조 — 일행 구성과 방문일 날씨에 맞춰 관광지를 추천하고, 가까운 응급의료기관·대피소·관광안내소 같은 대비 정보까지 함께 보여 주는 서비스

근거: 저장소 `main`의 코드와 `docs/10주차_작업기록.md`, `docs/11주차_작업기록.md`, `docs/근거자료.md`를 직접 읽어 정리했다. 확인하지 못한 것은 "확인 필요"로 표시했다.

- 전환 사유는 작업기록에 별도로 적혀 있지 않다.

## 2. 무엇이 다른가

1. **일행 전원을 기준으로 추천한다.** 나이대가 다른 일행의 선호 중 가장 낮은 값을 기준(최솟값 방식)으로 삼아, 한 사람만 좋아하는 곳이 위로 오르지 않게 한다.
2. **그날 날씨를 판단에 넣는다.** 방문일의 비·기온·미세먼지·특보를 기상청·에어코리아 예보로 확인해 실내/야외를 가른다. 어르신·아이가 있으면 더 엄격한 기준을 쓴다.
3. **판단 근거를 보여 준다.** "강수확률 70% → 실내"처럼 어떤 값이 기준을 넘어서 바뀌었는지, 날씨 때문에 제외된 곳이 어디인지 화면에 표시한다.
4. **가기 전에 대비 정보를 준다.** 가까운 응급의료기관·지진해일대피소·관광안내소와 거리, 준비물 체크리스트, 일행에게 필요한 무장애 편의 정보를 함께 보여 준다.
5. **기준값을 숨기지 않는다.** 날씨 기준은 `web/src/config/weatherThresholds.ts` 한 파일에 모여 있고, 공식 기준이 아니라 "팀 기준(안)"이라고 코드와 화면에 밝힌다.

## 6. 계산식과 이유

### 6-1. 날씨 판정 (`web/src/lib/weatherRules.ts`)
다음 중 하나라도 해당하면 실내만 추천한다.

| 조건 | 일반 | 어르신·아이 동반 |
|---|---|---|
| 강수확률 | 60% 이상 | 40% 이상 |
| 최저기온 | -5℃ 이하 | 0℃ 이하 |
| 최고기온 | 33℃ 이상 | 30℃ 이상 |
| 미세먼지(PM10·PM2.5 중 하나) | 나쁨(3) 이상 | 나쁨(3) 이상 |
| 비·눈 예보 | 있으면 | 있으면 |

- 강수확률 30%(동반 20%) 이상이면 야외도 추천하되 "비가 올 때 갈 실내 대안"을 함께 보여 준다.
- 호우·태풍·풍랑 특보(동반 시 강풍·대설 추가)가 있으면 바다·산·계곡을 제외한다.
- 방문일이 오늘부터 3일보다 멀면 "출발 2~3일 전에 다시 확인"을 안내한다.
- 여러 날 일정은 날짜별로 판정하고, 항목별로 가장 나쁜 값을 쓴다.

**이유**
- 어르신과 아이는 비·더위·추위에 더 취약하므로 같은 날씨에도 기준을 더 엄격하게 둔다.
- 최고기온 33℃는 기상청 폭염주의보 기준을 참고했다. 미세먼지는 환경부 행동요령이 민감군에게도 "나쁨"부터 실외활동을 줄이라고 안내하므로 동반 일행도 3으로 두었다.
- 단기예보는 3일 안쪽만 신뢰하기 때문에 그보다 먼 날짜에는 재확인을 안내한다.
- 모든 값은 공식 기준이 아니라 **팀이 정한 잠정값**이다.

### 6-2. 실내·야외 분류 (`attractionSetting.ts`)
관광지 이름·분류의 키워드(박물관, 미술관, 해변, 계곡 등)로 판단하고, 안 맞는 곳만 예외 목록에 적는다. 판단이 안 되면 **야외**로 본다.
- 이유: 관광지 데이터에 실내·야외 구분이 없다. 날씨가 나쁜 날 실내라고 잘못 추천하는 쪽이 더 위험하다.

### 6-3. 대비 정보 거리 (`preparedness.py`)
가까운 시설은 하버사인 직선거리로 찾는다. 좌표가 비었거나 국내 범위를 벗어난 항목은 제외한다.
- 이유: 별도 지도 API 없이 계산할 수 있고, MongoDB `$geoNear`와 비교했을 때 표본 5곳에서 같은 시설을 골랐다(거리 차이 0.1% 이내).
- 한계: 실제 이동 거리·시간과는 다르다.

### 6-4. 무장애 맞는 정도 (`tourapi/barrierfree.py`)
```
fitScore = 100 × (일행에게 필요한 시설 중 정보가 있는 항목 수) / (필요한 항목 수)
```
- 어르신: 주차·엘리베이터·화장실·경로·휠체어 / 아이: 유아차·수유실·유아용 의자·화장실
- 이유: 이동과 돌봄에 직접 필요한 시설이다.
- 한계: 시설이 실제로 있는지가 아니라 관광공사에 정보가 **등록돼 있는지**를 재는 값이다. 화면에도 그렇게 표시하며, 추천 순위에는 쓰지 않는다.

### 6-5. 지역 추천 (`indices.ts`, 파이썬 `indices/`)
```
LQ_ig  = (V_ig + k·s_g) / (V_i + k) / s_g          (k = 50)
Score  = LQ × log(V_i)
동행자 = min(LQ_g) × log(V_i)
관광지 = 인기 지표 × min(연령대별 태그 선호 가중치)
```
- 이유: 인기만 보면 큰 도시가 항상 이긴다. 해당 그룹이 전국 평균보다 몰리는 정도를 비교하고, k로 소규모 지역의 우연한 값을 완화하며, log(V_i)로 방문 규모를 약하게 반영한다. 동행자는 최솟값으로 가장 덜 만족하는 사람을 기준으로 삼는다.
- 한계: 입력인 성·연령 방문자 수와 연령대별 태그 가중치는 실데이터가 아니라 **샘플·가정값**이다.

## 8. 한계와 확인 필요

- 지역 추천의 성·연령 방문자 데이터가 샘플이다. DataLabService는 성·연령 분포를 제공하지 않아 해당 데이터셋은 미설정이다.
- 날씨 기준값은 잠정값이다.
- 에어코리아 측정소 좌표 축(dmX=위도 여부)과 단기예보 코드값 일부는 코드에 TODO로 남아 있어 실제 응답과 대조가 필요하다.
- 관광안내소 Open API는 활용신청 전이라 CSV로 대체한다.
- 배포 환경에는 MongoDB가 없다.
- 웹(web-tawny-nine-15.vercel.app)과 `tourapi-demo`는 배포가 끝났지만 **GitHub 푸시로 자동 배포되지 않는다.** `main`을 바꾸면 웹과 `tourapi`를 각각 직접 다시 배포해야 반영된다.
- 레이크의 날씨 데이터는 첫 실행(11/5)에서 기상청 API 403으로 0건이었다. 이후 날씨 연동은 동작하나 레이크 재실행 결과는 기록에 없다.

## 9. 향후 계획 (설계 단계, 미구현)

**사용자 평가 기반 맞춤 추천**
- 공공데이터로 시작하고, 방문 후 평가가 쌓이면 연령대·성별 맞춤으로 옮겨 간다.
- 방식: 1~5점 평가를 연령대별로 모아 전체 평균 대비 실측 선호도를 구하고, 평가 수에 비례해 기존 가중치와 섞는다(경험적 베이즈 방식).
```
O_ag   = R̄_ag / R̄_g                       (연령대 평균 대비 실측 선호도)
w_ag   = n_ag / (n_ag + m),  m = 10
A'_ag  = w_ag · O_ag + (1 − w_ag) · P_ag    (P: 기존 가중치, 0.6~1.4로 제한)
```
- 평가가 0건이면 지금 추천과 같고, 평가가 쌓일수록 실측값 쪽으로 옮긴다. 동행자 중 최저 선호도 기준은 유지한다.
- 필요: 평가 입력 화면, 평가 저장 DB(배포 환경용), 개인정보 처리방침, 평가 5건 미만은 지표 숨김.
